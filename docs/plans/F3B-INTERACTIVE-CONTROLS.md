## Creator outcome and scope

An ordinary editor creator and an independent native MCP creator each author a button in the existing HUD group, bind it to their own typed Application command, operate it during Play or Pause, observe committed state feedback and export the same interaction. Labels, constant arguments and application rules belong to creator content. Engine code supplies reusable input, presentation and guarded command delivery.

The existing group retains32total rows, shared style/corner layout and bundled font. A new button row has a static caption, stable command/binding references and a complete explicit typed constant argument map. No general layout framework, expressions, dynamic widgets, sliders/text entry, scene transitions, full menu designer or gamepad navigation enters this slice. Scene16/recovery14/next content capability evolve at their actual owners, with Descriptor5 retained absent launch-field changes. Old labels and paused compare-and-commit command APIs keep their behavior.

## Ordering and input contract

A new activation identifies one captured button/run/schema and a monotonic activation ID. Its constant arguments are resolved from immutable captured authoring on the execution owner. Normal intervening ticks do not invalidate an action intent; the owner applies it against its current committed revision. Existing paused dispatch still requires the caller's exact expected commit. One activation can be outstanding per UI/runtime owner, with an explicit bounded terminal result and no invisible retry queue.

The editor adds an ordinary worker request before its next due tick, retaining priority invalidation/Stop and mandatory acknowledgment backpressure. Activation failure preserves state and playback while exposing an error. Reset/Stop/replacement/authored invalidation/debug boundaries invalidate pending work. Native focus loss/Escape/canceled gestures invalidate unexecuted native work through a distinct epoch; programmatic activation has no desktop-focus requirement. Already owner-admitted work may commit once.

For exported applications with captured button rows, use an opted-in one-frame-buffered pipeline. Current safety/lifecycle cancellation precedes draining the previous completed UI frame's one intent and advancing previously admitted gameplay input. Then capture one presentation, prepare layout in the actual viewport, register controls before camera/picking, route current gameplay input for the next advance and paint the same prepared layout/scene. A click's feedback arrives on the next UI frame, including a requested repaint while paused. Previously admitted gameplay may execute before a newly observed click; that click's own events cannot enter gameplay. Existing nonbutton/code-first applications retain their prior ordering. Discarded/multiple UI passes cannot advance, drain or activate twice.

A button claims its full pointer gesture through release/cancel, including movement/resize/disable. Unavailable buttons block click-through and explain availability. Passive labels stay passive. Real Tab/Shift+Tab focus, nonrepeating Enter/Space and Escape ownership are required.

## Acceptance

- Independent editor/MCP authoring includes typed arguments, stable references, reordering, shared history, invalid-reference repair, unfinished numeric draft crash/Restore, save/reopen and exact export.
- Running and paused commands execute once at documented boundaries, expose acknowledgment/commit identity and produce coherent geometry/HUD feedback. Invalid/replayed/stale/schema/debug/busy requests preserve committed state. Existing paused semantics remain qualified.
- Actual native interaction covers mouse, keyboard, held/repeated keys, focus loss, Reset/Stop, disabled click-through, label wrapping near buttons, resize between press/release, discarded passes, compact/scaled layouts and visible errors.
- Both exact apps pass source-hidden value/activation checks and native input/placement/resize/normal-close checks. Older documents and incompatible-kit rejection retain their contracts.
- Freeze numerical investigation/retention criteria before candidate measurements, with rationale from the accepted baseline and frame budget. Compare no-button regressions and bounded button/activation work, idle and repeated-use retention. Separate CPU/input/VM/GPU/resource scopes, preserve adverse results and avoid reopening F2a profiling.

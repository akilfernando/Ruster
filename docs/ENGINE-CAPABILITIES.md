## LOD and ray tracing

LOD reduces geometry detail when it contributes less to the image. Plan mesh LOD alongside visibility culling, texture mipmaps and measured CPU/GPU/memory costs; they address different costs and are not interchangeable. Preserve artist control and source assets. Automatic simplification/import cost, transition artifacts and quality need real asset evidence. Current backface culling, mesh instancing and V2b cached mesh bounds are not evidence of frustum/occlusion culling or LOD support.

Ray tracing is a later quality/rendering path, potentially starting with a bounded effect such as reflections or shadows. It requires explicit hardware/API capability checks, acceleration-structure resource/update ownership, compatible materials, sampling/denoising and measured quality/cost. Keep an effective raster path; adding a ray-tracing checkbox would not deliver the workflow. This is a proposed adoption approach, not an accepted API/backend migration or a guarantee that the current abstraction already supports it.

Primary sources accessed2026-11-05: [Godot mesh LOD](https://docs.godotengine.org/en/stable/tutorials/3d/mesh_lod.html) documents import-time simplification, quality pitfalls and measuring effectiveness; [Epic hardware ray tracing](https://dev.epicgames.com/documentation/en-us/unreal-engine/hardware-ray-tracing-in-unreal-engine) documents hybrid raster/ray approaches, denoising, hardware conditions and scene-update costs. These inform tradeoffs, not Ruster capability or comparative-performance claims.

## Customer-project readiness assessment — 2026-11-09

This assessment is a recommendation based on inspected current owners and retained creator/runtime evidence. The user explicitly confirms creator-owned scoring/menu/application rules, supported by reusable engine facilities. It activates no new implementation or Goal-tool goal. Historical M0–M8 labels measure their original prototype contracts. They do not measure a percentage of the expanded engine product. Current public-alpha qualification remains incomplete.

The strongest delivered path is a small Linux interactive visual application with supported OBJ/PNG assets, opaque materials/lighting, authored transform behaviors, keyboard actions and bounded spatial interaction. Ordinary editor and native MCP routes can save/recover/reopen and deliver a standalone application. Rust application authors can additionally implement their own state, UI and completion through `ruster_app::Application`. Finishing a particular supported application is possible today, as the retained examples demonstrate. An independently adopted customer product built entirely through editor/Lua still needs broader game/application workflows.

| Project type | Current readiness judgment | Principal remaining obstacle |
| --- | --- | --- |
| Small exhibit, scripted mechanism or constrained interactive visual demonstration | Demonstrated end-to-end in retained bounded examples | Independent first-run adoption and named deployment/hardware support |
| Small code-first Linux game/application with custom egui interface | Feasible for a Rust developer inside supported limits | Developer supplies application mechanics/UI and any missing domain services; customer handoff/support remains unqualified |
| Complete editor/Lua-authored small game | Input and spatial motion are delivered foundations; complete reusable game loop is unfinished | Persistent per-run state, objectives/outcomes/restart and player-facing feedback, followed by selected sound/content needs |
| Character/action game or larger production | Substantial capability work remains | Composition/import, animation/physics, content scale, devices/platforms and production qualification according to the creation |

The highest-leverage next investigation is a bounded complete-play-loop slice. One small creator-authored game should start, respond to input and surroundings, track one objective, visibly report success/failure, restart cleanly and export through both creator paths. First investigate typed persistent per-run behavior state and a minimal reusable runtime-UI/feedback surface. Creators define their own scores, objectives, menus and rules. The example supplies application content and an acceptance exercise, while the engine facilities remain reusable. Preserve atomic failure/Reset behavior, guarded MCP observation and bounded work. Saving player progress to disk is a later separate slice unless the chosen creation needs it immediately.

This proposal addresses an inspected host API bottleneck. `ruster-behavior::Engine::evaluate_with_input` recreates the Lua module/environment and returns `Transform`; `ruster_app::Application` separately permits Rust-owned `ui`, `input`, `reset` and `completed`. Prefabs/hierarchy remain important for repeated construction but do not supply scores, objectives or player feedback. Audio, pointer/gamepad, reusable composition, richer import and animation/physics should follow from the chosen game's actual requirements. LOD/culling and later ray tracing retain their existing measured-scale/quality order.

Before calling that scope customer-ready, require an independent creator to build and finish a project from the guide, without engine-source patches or continuing author assistance. The exact application must package/reopen/recover and run on its advertised deployment environment, with meaningful quality/cost and UI/MCP evidence. NVIDIA native results are retained; Intel presentation and broader Linux binary compatibility remain unresolved qualifications. No numerical completion percentage or calendar delivery estimate is established by this assessment.

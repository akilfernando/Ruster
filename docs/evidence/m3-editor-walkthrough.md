# M3 editor: independent agent-assisted walkthrough

2026-11-04. This is one local, agent-assisted developer walkthrough against the native egui/eframe editor, not a human usability study. The walkthrough used the editor README as its starting guide and did not inspect UI implementation before trying the journey. The RTX 4060 Laptop GPU used Vulkan on Linux/Hyprland. The editor opened on workspace 2 while workspace 1 remained active. Input was injected into the exact editor process through the opt-in loopback egui inspection protocol; no global keyboard, pointer or clipboard input was used. The fixture and saved file were under `/tmp`.

The initially hidden workspace did not paint: GetTree returned an app-not-painting timeout. A temporary compositor rule for the editor class set `render_unfocused=true`, and the specific window was floated and resized. This enabled real frames, widget-tree inspection, and framebuffer capture without switching workspaces. Hidden/forced-background measurements are not representative of an interactive foreground session. The optional inspection feature is disabled by default. After testing, root reloaded the persistent compositor configuration to remove the temporary rule; config validation passed and workspace 1 remained active.

## Observations

- Starting with a copy of `examples/logistics.scenario.json`, Transport was selected and capacity changed from 2 to 4. Apply produced revision 1, an unsaved marker, and an explicit message that runtime needed a reset; the runtime still used its earlier values.
- Applying capacity 0 produced `transfer_per_tick must be greater than zero`, retained the invalid field, and preserved revision 1. Entering 5 and applying succeeded. Reset and Step showed tick 1, produced 3, delivered 3, and a supply-limited indication. This is a small throughput-inspection example, not a validation of real-world logistics models.
- Outside the text field, Ctrl+Z and Ctrl+Shift+Z restored capacity 4 and then 5. Runtime remained at tick 1 and delivered 3 throughout. Ctrl+Shift+S opened Save As. Attempting the existing fixture reported a file-exists error and preserved the work; entering a new path saved it. Ctrl+O reopened the saved file with capacity 5 and runtime tick reset to 0. The dialog moved vertically when the error appeared, so its controls had to be located again.
- A directed compositor close with an unapplied invalid 0 opened the unsaved-changes guard. Save and continue kept the guard open with the validation error. Escape canceled the guard and preserved the field. A second close followed by Discard and continue exited the test process.
- New opened an identity dialog; Create with the default ID produced a new unsaved scenario. Run changed to Pause and advanced to tick 13; Pause stopped it with produced 39, delivered 26, and source inventory 13. The scene identified a capacity bottleneck. Duplicate was not exercised.
- Tab focus was confirmed from the accessibility tree's focused node: Open → Save → Save As. Ctrl+A, Ctrl+Z, Ctrl+Shift+Z, Ctrl+Shift+S, Ctrl+O, and Escape were exercised. A 960×640 framebuffer was captured and inspected for readability, then the window was restored to 1400×900.
- The first screenshot exposed missing decorative glyphs. The implementation removed those decorations and a subsequent capture showed readable labels. The final [framebuffer](m3-editor.png) is from the corrected build after reset and one tick: authored/runtime capacity 4, produced 3, delivered 3. It is a real captured frame, not a mockup.

## Recovery finding and retest

A later focused pass found that after 5 → 4 Apply, 0 Apply, and restoring 4, the validation message remained even though the field matched the last valid authored value and Apply/Revert were disabled. After the fix, the same sequence in a newly launched native editor cleared the field validation message automatically when 4 was restored. This retest did not repeat the whole journey.

One monotonic scoped-automation sequence on the corrected debug inspection build took 0.537 s from the start of the 5 → 4 edit to confirmed Apply, 1.069 s from that same start to confirmed invalid-0 feedback, and 1.469 s from that start to confirmed recovery on re-entering 4 (0.400 s after feedback). These include injected event frames and tree requests under forced-background rendering. They are neither human task times nor release-build latency benchmarks. Earlier attempts to time a larger create/edit/save flow failed to account for the New dialog and transition; no end-to-end time is claimed.

Before forced rendering or inspection polling, the initial debug inspection process consumed 1 CPU tick over 3.000 s with `CLK_TCK=100`, or about 0.33% of one core, on the hidden workspace. This brief idle sample is not a visible-window or release performance benchmark.

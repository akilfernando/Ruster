# M8 native content and recovery journey

2026-11-04. This records a bounded native inspection journey on the local Linux/Hyprland workstation, not a human usability study. The inspection-enabled editor used a disposable copy of `examples/content` with independent absolute `RUSTER_EDITOR_STATE` and `RUSTER_RECOVERY_DIR`. Windows were 1400×1000, `org.ruster.editor`, on workspace 2. The user’s active workspace was 3 for the first phase and 1 for later phases; the user changed it between phases. Each interaction call checked that the active workspace remained unchanged, the PID/class/title/workspace matched, and the IPv4 loopback inspection listener belonged to the target process. No global input, fake focus event, clipboard replacement or workspace switch was used. The root controlled launches, crashes and the temporary editor-scoped background-rendering rule; the rule was removed and the Hyprland configuration compared equal after the run.

The [driver](M8-content-recovery-native.py) injected events into the app’s inspection interface. Its success means those events were delivered; conclusions below also inspect trees, files, hashes and actual application state. It does not prove physical focused input or experienced Unity/Unreal familiarity. Background rendering was altered for the hidden window; no performance claim is made.

## Observations

- Hierarchy search for `right` showed one hidden selected object while the inspector still identified `left`. Enter selected the visible `right`; Escape cleared the filter when the search field owned focus. Content search for `Ready` showed the matching pyramid. A contextual source rename, submitted with focused Enter, moved the disposable OBJ and persisted the catalog independently of scene Undo.
- App-injected internal drag assigned pyramid to `center`, while `right` remained the active inspector object. The scene advanced to revision 2. One Undo restored `center` to a procedural cube at revision 3, and the renamed catalog entry remained. The [frame after the drop](m8-content-recovery-drag.png) shows the target and status; the saved scene and subsequent tree provide the Undo evidence. Physical focused drag remains separate.
- At 2× UI scale the [asset dialog capture](m8-content-recovery-2x.png) showed the content and its controls within the captured window. This is one targeted inspection, not broad scale or accessibility acceptance. The framebuffer request was unaltered at one pixel per egui point; the 2× capture is 700×500 pixels for the 1400×1000 window.
- A saved asset-bearing baseline had `left` using pyramid and `center` procedural. A real worker checkpoint contained selected `center`’s invalid precision draft `-`, while its authored translation stayed `[0, 0, 0]`. The raw checkpoint and embedded document hashes and both scene/catalog origins were verified before the root deliberately sent SIGKILL. The first process exited `-9`; this was an intentional crash, not a clean shutdown.
- On the no-argument relaunch, explicit **Restore as unsaved copy** restored the invalid draft and the Ready asset catalog. The checkpoint owner lock remained held. After replacing the draft with `0` and submitting Enter, an external change to the disposable original was preserved: Save As to that original failed with “scene changed on disk or destination exists” and its SHA-256 remained `8dc1f1cd1976a38f709e2f9c0f3af185c8f25a06876f7c200736c3ee59b01276`. Save to a fresh sibling preserved the recovered scene, retired all `window-*` journals after the worker boundary, and normal menu Close exited `0`.
- In a separate clean-scene case, an invalid translation offset alone was checkpointed as `-` with the authored `left` translation still `[-2, 0, 0]`. Reset restored `0` and the clean transition retired the journal. This verifies checkpoint capture and reset, not a crash-and-restore of the offset.
- A separate pending-name checkpoint contained `Pending recovered name` while the authored `left` name remained unset. After the second intentional SIGKILL (`-9`), explicit restore showed that exact text in the [rename dialog](m8-content-recovery-pending-name.png), with `left` still the authored object name. Cancel left the name unsubmitted.
- For a controlled cleanup conflict, the test changed only the owned disposable journal’s sequence after its checkpoint had settled, preserving a valid record and the original embedded document bytes. Close → Discard reported [recovery cleanup failure](m8-content-recovery-conflict.png) and offered **Close anyway** or **Cancel closing**. Close anyway exited `0` and preserved the replacement journal byte-for-byte. That intentionally retained record in the temporary fixture is evidence, not an unexpected store leak; the ordinary fresh-save retirement above is a separate successful case.

## Failures and limits

The first attempt to enter both an invalid precision draft and an invalid offset in the same session left the offset at `0`; the 35-second wait for both drafts timed out. The separate offset-only case above passed, but does not establish simultaneous draft capture. The first attempt to click **Revert transform components** targeted a control outside the visible window and did not remove the draft; entering `0` and pressing Enter repaired it. These attempts and action logs are retained. An earlier controller pilot received stdin EOF immediately, causing the tool to reap its editor before any interaction; no normal editor exit is claimed for it. Its failure record and log are retained.

The baseline Save succeeded and no `window-*` record was present afterward, but the run does not establish that this Save occurred before the first possible autosave. The close-conflict case tested **Close anyway**, not **Cancel closing** or physical window-manager close. One saved framebuffer immediately after the first restore was stale; the corresponding tree and subsequent file/checkpoint observations, not that frame, support the restore claim. Screenshots and inspection-injected keyboard events do not replace actual physical focus, keyboard traversal, or creator walkthroughs.
